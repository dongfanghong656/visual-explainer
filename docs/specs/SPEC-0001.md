# SPEC-0001 — Task Proof architecture and behavior

- Status: ACCEPTED_CURRENT
- Protocol version: 1.0.0
- Package candidate: 0.11.0-alpha.1
- Requirements: REQ-0001 through REQ-0005

## 1. System context

Task Proof is an additive extension to visual-explainer. The host model gathers project evidence and constructs a protocol bundle. Local code captures Git metadata, validates structural truthfulness, and deterministically renders HTML. A separate reviewer run uses the same protocol but owns its evidence and verdict.

```text
Author agent
  → exact Git snapshot
  → task-claim JSON
  → executable validation
  → amber HTML + JSON sidecar

Reviewer run
  → validate author claim
  → fresh exact Git snapshot
  → independent checks/evidence
  → task-review JSON
  → executable validation
  → corrected review HTML + combined sidecar
```

## 2. Component architecture

| Component | Responsibility | Must not do |
|---|---|---|
| `PROTOCOL.md` | Human/agent rules and status semantics | Override executable validation silently |
| `schema.json` | Portable data shape | Claim semantic proof |
| `validation.mjs` | Cross-field and evidence/status invariants | Inspect code or decide correctness |
| `git-snapshot.mjs` | Exact local Git scope and digest | Return patches, leave launch directory, write repository |
| `render.mjs` | Deterministic safe HTML projection | Change verdicts or hide overflow |
| MCP server | Expose tools/prompts/resources and write approved output | Call an LLM, network service, or remote storage |
| Skill/commands | Direct author and reviewer behavior | Treat prose/diagram as evidence |

## 3. Author claim model

Required top-level identity:

- `schemaVersion=1.0.0` and `kind=task-claim`;
- stable claim/task ID and creation time;
- project/repository identity;
- author name, role, and run ID;
- exact scope: branch, base revision, head revision, dirty flag, optional paths, required dirty digest.

Required task/logic state:

- objective and measurable acceptance criteria;
- one-sentence change thesis;
- actors, events, invariants, termination;
- Done/Doing/Next/Blocked lanes;
- evidence registry, risks, unknowns;
- completion claim and independent artifact axes.

Allowed completion values are author-only: `claimed-complete`, `claimed-partial`, `blocked`, `not-claimed`.
The author artifact verification axis may describe observed testing or external validation, but it may not use `ACCEPTANCE_PASSED`; acceptance belongs to the reviewer/release workflow.

## 4. Reviewer model

A review contains:

- stable review ID, creation time, reviewer identity, distinct run ID;
- exact reviewed scope;
- reviewer-owned evidence registry;
- one result for every claim criterion;
- explicit mechanism claim checks;
- discrepancies and residual risks;
- overall verdict and corrected completion.

Allowed overall verdicts: `accepted`, `partially-accepted`, `rejected`, `blocked`, `stale`.

The exact mapping is fixed:

| Overall verdict | Corrected completion |
|---|---|
| accepted | verified-complete |
| partially-accepted | verified-partial |
| rejected | not-verified |
| blocked | blocked |
| stale | not-verified |

## 5. Causal logic grammar

Actors are stable responsibilities/state owners. Events have stable IDs, source, target, labeled action, phase, optional precondition/effect, and evidence references. Phases are `before`, `change`, `after`, `interrupt`, and `verification`.

Invariants describe prohibited states or ownership/write rules. Termination describes when the process stops, cancels, or yields control. The host prompt must examine normal, stale/concurrent, user interrupt, error/fallback, and lifecycle paths.

The primary sequence-like figure shows at most eight actors and sixteen drawable events. If the bundle is denser, the caption discloses omitted counts and the full event registry remains visible and authoritative.

## 6. Evidence model

Evidence has stable ID, type, summary, locator, producer, optional observed time/revision/environment/limitations, and command result fields where applicable.

Command evidence of type test/build/lint requires command, result, and matching exit code for pass/fail. Reviewer evidence cannot be produced by the author agent. `git-snapshot` and `claim-reference` are scope/context-only evidence: a verified or contradicted criterion/event/invariant must also cite at least one substantive reviewer observation, such as source/diff inspection, a test/build/lint run, a runtime trace, or external validation. Verified items cannot cite failing command evidence as support.

Scope evidence is distinct from behavior evidence. Clean scope binds to head revision; dirty scope binds to SHA-256 snapshot digest.

## 7. Validation invariants

Author `claimed-complete` requires:

- all criteria `claimed-pass`;
- Done nonempty;
- no Doing or Blocked entries;
- evidence on every Done item and pass criterion;
- objective evidence;
- exact Git-snapshot evidence;
- no author-declared `RELEASED`.

Reviewer `accepted` requires:

- valid author claim;
- distinct run ID;
- exact branch/base/head/dirty/digest match;
- reviewer Git snapshot;
- every criterion verified once;
- no contradiction;
- at least one explicit mechanism check;
- exact verdict/completion mapping.

## 8. Git snapshot and security

The snapshot tool resolves the MCP launch directory as its root, accepts only a relative directory within it, resolves the repository root, and rejects escapes. It uses Git subprocess arguments without a shell.

The dirty digest hashes:

- head revision;
- normalized status entries;
- SHA-256 of tracked binary diff;
- Git object hashes of untracked file contents.

The tool returns metadata, paths, stats, and digest—not patch bodies. Output filenames are basename-only. Existing output symlinks and a symlinked output directory are rejected. HTML content is escaped by the deterministic renderer.

## 9. MCP interface

Task Proof tools:

1. `task_proof_git_snapshot`
2. `task_proof_validate_claim`
3. `task_proof_render_claim`
4. `task_proof_validate_review`
5. `task_proof_render_review`

Render tools write under `~/.agent/diagrams/`, default to not opening a viewer, and create HTML plus a `.task-proof.json` sidecar. The JSON source bundle is written before the deterministic HTML derivative so a failed second write remains recoverable, although cross-file atomicity is not guaranteed in the alpha. Protocol, schema, examples, and command templates are exposed as read-only resources/prompts.

The generic upstream tools remain available. Pi's native extension remains generic; Task Proof alpha requires the local MCP server or direct modules unless Pi is separately configured to use that server.

## 10. Failure behavior and limitations

- Invalid bundles are not rendered.
- Stale scope cannot be accepted.
- Missing environment or external evidence becomes blocked/not-assessed.
- Renderer/validator success does not prove implementation correctness.
- The two output files are not a cross-file atomic transaction; partial output is possible on a filesystem failure and is tracked as RSK-0003.
- A full MCP stdio client handshake is required for user-usable status and remains pending.
- Same-model separate-run review is weaker than different-model/human/CI review.

## 11. Compatibility

Task Proof is additive. Existing visual explanation, quick mode, slide, Mermaid, and general MCP registrations must remain present. Package, marketplace, plugin, and skill versions must match the candidate version.
