# Task Contract Authority Protocol 2.3

## Status

- Protocol version: `2.3.0`
- Authority receipt version: `1.2.0`
- Implementation: `contract-authority.mjs`
- Portable schema: `task-contract.schema.json`
- Example: `examples/task-contract.example.json`
- Integration status: contract core only; public Claim/Review/MCP enforcement remains a separate gate.

## Purpose

Task Proof must not let an implementation agent choose a convenient subset of the real requirements, prove only that subset, and then display a green completion verdict. A task contract is frozen before final acceptance and becomes the authority for task identity, repository scope, source requirements, coverage, criteria, evidence policy, reviewer procedure, amendments, and revocation.

A Claim and Review may copy the contract for display, but they cannot redefine it.

## Trust chain

```text
Authority sources
    ↓ source requirements + coverage decisions
Frozen task contract
    ↓ deterministic contract digest
Author claim
    ↓ exact criterion snapshot + Git scope
Authority verification receipt
    ↓ generated by the final reviewer through a trusted adapter
Reviewer artifact
    ↓ claim digest + contract + receipt + procedural attestation
Final gate
```

## Contract digest

The executable validator normalizes all accepted fields, rejects unknown fields, sorts set-like arrays and stable-ID collections deterministically, permits safe integers only, and hashes canonical UTF-8 JSON with SHA-256.

The digest binds all authority declarations, sources, scope, requirements, criteria, named-check policies, review policy, lifecycle, and amendment lineage. Changing any of these values creates a different contract.

## Authority levels

| Level | Meaning | Maximum without verified adapter |
|---|---|---|
| `claimant_provisional` | constructed by the implementing agent | `INCONCLUSIVE` |
| `user_attested` | derived from a user instruction | `INCONCLUSIVE` |
| `project_approved` | bound to an immutable repository source | `INCONCLUSIVE` |
| `issue_locked` | bound to a live issue record | `INCONCLUSIVE` |
| `release_policy` | bound to repository or release-registry policy | `INCONCLUSIVE` |

A textual level or assurance label is never sufficient. PASS authority requires a receipt that is revalidated through a trusted adapter during the final reviewer run.

## Source requirements and coverage

Each explicit requirement is represented separately from the acceptance criteria and has one disposition: `covered`, `explicitly_excluded`, `deferred_with_authority`, or `superseded`. A non-covered requirement requires an authority reason and caps source coverage at `PASS_WITH_LIMITS`. A missing or invalid mapping is a protocol failure.

This mapping proves only that the recorded source requirements are handled. Extracting every requirement from a user message or external document remains an adapter/reviewer responsibility and must be disclosed.

## Named-check freezing

A criterion that requires `named-check:<id>` also requires a frozen policy entry containing the policy digest, evidence kind, executable digest, argument digest, and working directory. A receipt with the same check name but different command semantics does not satisfy the criterion.

## Authority receipt

The receipt is bound to the contract, source, repository, implementation base and exact Claim HEAD, final reviewer run, observation time, adapter identity, source ancestry and immutability, safe Git configuration, file type, byte size, and SHA-256.

Receipt integrity is tamper-evident. It is not cryptographic identity unless a trusted adapter actually verifies a signature. A final reviewer must generate or revalidate the receipt. A receipt created by the claimant or another reviewer run is rejected.

## Reviewer binding

A passing Review must include a full Review artifact, reviewer role and run identity, attestation session binding, Claim digest, contract ID and digest, authority declaration digest, authority verification receipt digest, correct chronology, and a procedure level at least the contract minimum.

R2 requires reconstruction before reading the Claim and independent evidence. R3 additionally requires adversarial evidence.

## Final gate

```text
finalGate = minimum(
  evidenceGate,
  authorityCap,
  sourceCoverageCap,
  reviewerCap,
  namedCheckPolicyCap,
  contractLifecycleCap,
  artifactLifecycleCap
)
```

Results are `PASS`, `PASS_WITH_LIMITS`, `INCONCLUSIVE`, `STALE`, or `FAIL`. Hard digest, identity, chronology, or receipt-binding mismatches produce FAIL. Missing independent review or missing trusted authority adapter produces INCONCLUSIVE.

## Lifecycle

- `active`: contract may be used;
- `superseded`: old Claims and Reviews are STALE;
- `revoked`: final gate is FAIL.

An amendment creates a new contract and links the previous contract ID/digest, authorizing receipt, reason, and effective revision. It does not overwrite history.

## Limits

Protocol 2.3 does not by itself prove cryptographic identity, completeness of requirement extraction, semantic correctness of tests, behavior outside the specified environment, merge, publication, deployment, hardware validation, scientific validity, or user outcomes. Those remain distinct evidence and lifecycle gates.
